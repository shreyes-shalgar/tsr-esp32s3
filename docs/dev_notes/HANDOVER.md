# Handing this project to GitHub Copilot agent mode

Everything in this folder drops into the repository root. Copilot picks it up
automatically — no configuration beyond two VS Code settings.

---

## The decision I made for you, and why

**Copilot builds on the verified baseline. It does not rebuild from scratch.**

You already have a solution measured at 99.45 % accuracy with 27,648 B of peak
RAM, whose C kernel is bit-exact against TensorFlow Lite across all 364
validation images. Handing an agent a blank repo and asking it to beat that is a
bad trade: it would spend its first several hours rediscovering the traps in
`AGENTS.md` section 4 — the two different TFLite rounding rules, the XNNPACK
delegate, the ring-buffer byte loss — and would most likely land somewhere
worse, with no way to know it had.

So the handover is framed as **adopt, verify, then improve in priority order**.
If you specifically want an independent second attempt to compare against, see
the appendix at the end.

The single most important file here is `scripts/verify_all.py`. An autonomous
agent's dominant failure mode is reporting an improvement it never measured.
That script is the answer: one command that builds both boards, checks
bit-exactness, runs all 364 images over the real UART on QEMU, and prints
pass/fail. Every agent instruction points at it, and the rule is stated three
separate times: *never report a number you did not measure.*

## What goes where

The gate expects the submission layout — `src/qemu_app/` for the firmware,
`scripts/` for the host tools, `model/` for the `.tflite` files, `out/data.npz`
for the prepared validation set, and `test/host_test.c` for the native harness.
That is the structure the submission zip already has; drop `out/data.npz` in
from your working tree (it is regenerated by `python src/prepare_data.py`).

```
<repo root>/
├── AGENTS.md                                   ← the project contract
├── scripts/verify_all.py                       ← the gate
├── test/host_test.c                            ← native harness the gate compiles
└── .github/
    ├── copilot-instructions.md                 ← always-on rules
    ├── instructions/
    │   ├── firmware.instructions.md            ← auto-applies to src/qemu_app/**
    │   └── ml.instructions.md                  ← auto-applies to src/**/*.py
    ├── agents/
    │   ├── tsr-lead.agent.md                   ← orchestrator, delegates
    │   ├── tsr-ml.agent.md                     ← model, augmentation, quantisation
    │   ├── tsr-kernel.agent.md                 ← int8 C runtime + bit-exactness
    │   ├── tsr-firmware.agent.md               ← Zephyr, UART, board builds
    │   └── tsr-bench.agent.md                  ← measures, never fixes
    └── prompts/
        ├── onboard.prompt.md
        ├── optimize-speed.prompt.md
        ├── harden-domain.prompt.md
        └── ship.prompt.md
```

`AGENTS.md` and `.github/copilot-instructions.md` are both always applied. The
`.instructions.md` files attach themselves by glob, so the C rules only appear
when firmware files are in context — that keeps the prompt focused.

## Setup

1. Copy this folder's contents into your repo root, merging with what is there.
2. In VS Code settings, confirm:
   - `chat.useAgentsMdFile` → **on** (so `AGENTS.md` is read)
   - `chat.todoListTool.enabled` → **on** (agent mode plans multi-step work)
3. Open the Chat view, switch the dropdown to **Agent**, then pick **tsr-lead**
   from the agent selector.

If the agent selector does not list `tsr-lead`, your VS Code is older than
custom-agent support — update it, or fall back to plain agent mode, which will
still read `AGENTS.md` and the instructions files but will not delegate.

## Model selection

Names in the picker change every few weeks, so choose by **tier**, not by name:

| Agent | Tier | Why |
|---|---|---|
| `tsr-lead` | strongest reasoning available | It decides what to keep and what to revert. This is where a wrong call is most expensive. |
| `tsr-kernel` | strongest reasoning available | Fixed-point rounding equivalence is the hardest reasoning in the project, and the easiest place to be confidently wrong. |
| `tsr-ml` | strong | Experiment design and reading noisy 364-image deltas correctly. |
| `tsr-firmware` | strong | Protocol precision matters more than raw reasoning. |
| `tsr-bench` | mid-tier is fine | It runs commands and reports output. Do not spend premium requests here. |

The `.agent.md` files ship with `model:` set to a current Claude Opus / Sonnet
identifier. **Edit that line to whatever your picker actually offers** — an
unrecognised model id makes the agent fall back to the picker default silently,
which is survivable but not what you chose.

Raise reasoning effort where the picker exposes it, for `tsr-lead` and
`tsr-kernel` only. The other three are throughput work.

## Running it

Type `/` in chat to invoke a prompt file.

**Session 1 — `/onboard`.** Establishes ground truth. It reads `AGENTS.md`, runs
the full gate, reports the measured baseline, and proposes its top three
improvements ranked by expected value. It is instructed not to edit anything and
to stop and ask before starting work. Read its three proposals carefully — this
is your best signal for whether the model understood the project or is pattern-
matching.

**Session 2 — `/optimize-speed`.** The highest-value remaining work. Inference
performance is 15 % of the score and tie-breaker #2, and the convolution kernel
is plain unoptimised C — nobody has touched it. The prompt enforces one change
at a time, with a revert on any bit-exactness break.

**Session 3 — `/harden-domain`.** The largest *risk*, as distinct from the
largest opportunity. Seven of seventeen classes exist only as 32×32
pre-augmented crops; if the hidden test set shows them as photographs, accuracy
there falls and the validation score would never have warned you. This prompt
builds a stress set to estimate that exposure.

**Session 4 — `/ship`.** Full gate, structure check, clean-room extract-and-build
verification, and a documentation-drift check against the measured numbers.

Run them as separate sessions. Agent context degrades over long autonomous runs,
and the gate between phases is what catches it.

## When to intervene

Stop the agent and reset if you see any of these — they are the observed failure
modes for this specific project:

- **A number without a command behind it.** "This should improve inference to
  around 6 ms" is the tell. Ask which invocation produced it.
- **Bit-exactness reported as "close" or "within tolerance".** The property is
  exact or it is broken. 363/364 is broken.
- **A comment being deleted as redundant.** The comments explaining the two
  rounding rules and the polled RX exist because the code beneath them looks
  wrong until you know why. An agent tidying them is about to undo the fix.
- **More than one change in flight before a gate run.** When the gate then
  fails, the agent cannot attribute it, and will usually start guessing.
- **Enthusiasm about depthwise convolutions, TensorFlow Lite Micro, or CMSIS-NN.**
  All three are reasonable-sounding and all three lose here: the first is
  memory-bandwidth bound, the other two add a dependency the project
  deliberately does not have.

## What is genuinely left to win

In descending order of expected value:

1. **Kernel speed.** Untouched. 15 % of the score plus a tie-breaker.
2. **Peak RAM**, via a narrower widest activation. Tie-breaker #1, decided
   outright by one number.
3. **Domain robustness** for the pictogram classes. Insurance against the one
   scenario that could cost real accuracy on the hidden set.
4. **Nothing else.** Specifically, do not let it chase the two remaining
   validation errors. They are the 83↔84 mirror pair, intrinsically ambiguous in
   this labelling, and both already report ~57 % confidence — the model is
   signalling its uncertainty correctly. Spending parameters there trades the
   RAM tie-breaker for a rounding error in accuracy.

## Appendix — if you want an independent second attempt

There is a real argument for it: a clean-room build gives you a second data
point and might find something this approach missed. If you do it, keep them in
separate branches and gate both with the same `verify_all.py`, so the comparison
is like-for-like.

To run it that way: give Copilot `AGENTS.md` sections 1, 2 and 4 (the goal, the
constraints, and the traps) but **withhold section 3** (the baseline metrics), so
it is not anchored to the existing architecture. Keep the traps — withholding
those buys you nothing but wasted hours rediscovering them.

Then compare on the gate output, not on the write-up. Whichever branch measures
better is the one you submit.
